## 3. Entity Lifecycles & Consumers

### 3.1 Assessments
- **Creation**: Handled in `api/src/routes/assessments.ts` via `POST /api/assessments`. The request receives an assessment questionnaire payload, generates an `assessment_id` (e.g. `ASM_...`), and saves the initial job state (`status: 'in_progress', progress: 0`).
- **Reading**: Queried by the frontend polling loop via `GET /api/assessments/:id`, and by dashboard landing via `GET /api/assessments/latest`.
- **Status Updates**: Background worker advances progress:
  - 30%: Playwright website crawling & evidence capture.
  - 60%: RAG statutory snapshot freezing & 10-model LLM gateway evaluation.
  - 90%: Grounding validation & Trust Score computation.
  - 100%: Completed assessment persisted with findings and scores.

### 3.2 Website Scans
- **Creation**: Generated by free scans (`POST /api/scans`) or triggered as Step 1 of authenticated assessments.
- **Reading**: Retrieved via `GET /api/scans/:id`.
- **Content**: Contains target URL, resolved IP, TLS version, security headers, cookie inventory, and preliminary readiness score.

### 3.3 Risk Findings
- **Creation**: Emitted by `LLMGateway` for each evaluated canonical control, validated by `GroundingValidator`, and saved via `db.saveFindings()`.
- **Reading**: Served by `GET /api/findings` and `/api/findings/:id`. Contains severity, verdict (`SUPPORTED`, `NOT_SUPPORTED`, `PARTIALLY_SUPPORTED`), verbatim statutory quotes, and actionable engineering remediation steps.

### 3.4 Trust Scores
- **Creation**: Calculated deterministically by `computeModelTrustScore()` and `computeTopThreeMajorityVoting()`.
- **Reading**: Served by `GET /api/trust-score/:id` and consumed by the PDF generator. Contains overall score (0–100), posture band, pillar breakdown, and evidence coverage percentage.

### 3.5 Benchmark Runs
- **Creation**: Created for every assessment and on-demand via `POST /api/benchmark/run`.
- **Reading**: Served by `GET /api/benchmark/latest` and `GET /api/benchmark/models`. Contains real-time execution states for all 10 candidate models, RAG context hash, and consensus synthesis.

### 3.6 Legal Knowledge Base
- **Storage**: Master source is `backend/knowledge/authoritative_corpus.json` (83 chunks).
- **Vectors**: Embedded with `sentence-transformers/all-MiniLM-L6-v2` into 384-dimensional dense vectors.
- **Consumption**: Queried by `StatutoryRAGRetriever` via Okapi BM25 and by Python `backend/rag/retrieval.py` via FAISS.

## 4. Authentication Architecture & RLS Identity Strategy

### Current Frontend Auth State
- The React frontend uses client-side session management stored in `localStorage` under `trustforge.session` (`AuthContext.tsx`).
- Demo profiles include `DEMO_USER` (Technova Solutions, Org ID: `org_technova`) and `ADMIN_USER`.

### Identity Mapping & Security Protocol
1. **Never Trust Raw Client Org IDs**: The Express API must validate the session or API token and bind operations to the authenticated user's verified organization.
2. **PostgreSQL RLS Context**:
   - Queries executed on behalf of authenticated users will set `app.current_user_id` and `app.current_org_id` in PostgreSQL session settings, or use Supabase JWT auth.
   - For backend orchestrator service workers, explicit service-role authorization is utilized with audit logging.
3. **Tenant Isolation**: RLS policies enforce that users can strictly read and write records where `organisation_id` matches their membership, completely preventing cross-tenant leakage between Organisation A and Organisation B.

## 5. Storage Mode Architecture: SUPABASE vs. LOCAL

To guarantee uninterrupted service across local development, testing, and production deployment:
- **`DATABASE_MODE=supabase`**: The primary operational mode when `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` (or `SUPABASE_ANON_KEY`) are present.
- **`DATABASE_MODE=local`**: Safe, resilient file-backed fallback using `api/data/*.json`.
- **No Split-Brain Reads**: The repository abstraction provides a unified interface. Reads and writes are directed exclusively to the active storage mode, with bidirectional migration scripts for syncing.
